# O'Neil v2 Windows 운영 준비안

## 현재 상태

상시 켜둘 Windows PC를 운영 후보로 삼되, 실제 연결·설치·자동 시작 등록은 하지
않았습니다. 이 패키지는 오프라인 검증과 설치 계획용입니다. 기존 자동매매,
대시보드, 계정, DB, 스케줄, 보유 종목은 변경하지 않습니다. 실거래 실행 파일,
로그인 생성 기능, 주문 전송 기능, 실거래 활성화 버튼은 제공하지 않습니다.

운영용 호스트와 HTTPS 인증 발급자가 아직 완성되지 않았으므로 실행 서비스가
이미 준비됐다고 볼 수 없습니다. ZIP을 풀거나 테스트를 통과하는 것만으로 주문
프로그램을 실행할 수 없고, 실행해서도 안 됩니다.

이 조합본은 공통 기반 `5fd6730` 위의 정책/계획 `eebd0b8`, 엄격한 정책 admission
`74ca1369`, Windows 운영 준비 `904c216d`를 보존하여 병합했습니다. 정책 admission과
테스트가 포함되며, 최종 소스 커밋은 ZIP의 MANIFEST.json에서 확인합니다. 추가로
전체 오프라인 검사·패키지 완전성·Windows 문자 인코딩·시간대 누락 검사를 보완했습니다.
최신 워커의 엄격한 정책 증거 기본값을 유지하고, fixture-only 시험 모드를 운영
설정으로 활성화하지 않습니다. 정책 통합은 실거래 또는 서비스 구현을 뜻하지 않습니다.

## 1. 운영 구조와 Windows 방식 선택

목표 구조는 한 계정에 하나의 장기 실행 워커, 영속 PostgreSQL 큐,
읽기 전용 인증 모니터, 영속 명령 저널, 프로세스 감독과 별도의 상태 감시입니다.
GitHub Actions는 빌드·검증용이며 1분/5분마다 새 주문 프로세스를 띄우는 큐가
아닙니다. 프로세스가 다시 시작되어도 주문을 다시 보내지는 않습니다.

추천 후보는 Windows 기본 **Task Scheduler**입니다. 추가 유료 제품을 전제하지
않지만, PC 전기·인터넷·기존 서비스 비용이 0원이라고 보장하지 않습니다.
초기 시뮬레이션은 사용자 로그인 후 수동 실행으로 검증하고, 실제 감독 실행 파일이
검증된 뒤 자동 시작 방식을 별도로 확정합니다. 단순 python.exe 명령을 Windows
서비스로 등록하는 방식은 피합니다. SCM에는 서비스 수명주기를 처리하는 호스트가
필요하며, 현재 소스에는 그 호스트가 없습니다.

작업 스케줄러 후보 설정은 다음과 같습니다. **여기에는 등록 스크립트나 활성화된
작업 XML을 넣지 않았습니다.** 아래 값은 검토 계획이며 적용된 설정이 아닙니다.

| 항목 | 검토할 설정과 이유 |
|---|---|
| 실행 계정 | 별도 검토된 최소 권한 계정. SYSTEM·관리자 권한을 기본값으로 쓰지 않음 |
| 실행 방식 | 절대 경로의 검증된 호스트와 작업 폴더. 셸 문자열·원격 코드 로딩 금지 |
| 트리거 | 검증 단계는 수동. 승인 후 로그온 또는 부팅 지연 트리거를 선택 |
| 중복 인스턴스 | IgnoreNew. Queue/Parallel 금지. DB 계정 잠금도 별도로 필수 |
| 다시 시작 | 실패 시 제한 횟수. 감독기와 스케줄러 두 층에서 재시작 폭주 금지 |
| 실행 시간 | 장기 실행용 명시적 제한 검토. 기본 최대 실행시간에 의존하지 않음 |
| 네트워크 조건 | 로컬 네트워크 사용 가능 여부는 참고만. 실제 DB·브로커 증거로 판단 |
| 배터리·전원 | 갑작스러운 강제 종료를 시험하고 복구. 기존 전원 설정은 변경하지 않음 |
| 절전 해제 | WakeToRun은 지속적인 절전 방지와 다름. 자동 적용하지 않음 |
| 보안 | 실행 정책 우회·방화벽·백신·VPN·인증서 검증 해제 금지 |

Microsoft의 [설정 문서](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtasksettingsset?view=windowsserver2025-ps)는
중복 실행, 실패 재시작, 네트워크 조건, 실행시간, 절전 해제 항목을 설명합니다.
이들은 서비스 건강 상태나 주문 안전성을 대신하지 않습니다.

"사용자 로그온 여부에 관계없이 실행"은 자격 증명·로그온 권한 검토가 필요합니다.
S4U는 암호를 저장하지 않는 대신 네트워크와 암호화 파일 접근이 제한됩니다.
이를 만능 무암호 운영 해법으로 쓰지 않습니다.
[Microsoft의 작업 보안 컨텍스트](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)와
[LogonType 문서](https://learn.microsoft.com/en-nz/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element)를
기준으로 실제 Windows 버전과 계정에 맞게 검증해야 합니다.

## 2. 오프라인 패키지 확인

1. ZIP SHA-256을 별도로 받은 신뢰 가능한 배포 메시지의 해시와 비교합니다.
2. ZIP은 v2 소스·테스트·운영 문서와 MANIFEST.json만 포함합니다.
   .env, 실제 계정, SQLite/DB 파일, 토큰, 기존 실거래 스크립트는 내보내지 않습니다.
3. 무결성 검사기는 ZIP 내부 파일 목록, 경로, 크기, SHA-256을 검사합니다.
   일치한다는 것은 손상 검증이지 작성자 신원이나 코드 안전성 보장이 아닙니다.
4. 사용자 소유의 새 로컬 폴더에 풉니다. 기존 운영 폴더에 덮어쓰지 않습니다.
   OneDrive·Dropbox·네트워크 공유의 동기화 대상 폴더는 활성 저널에 쓰지 않습니다.
5. Python이 없다면 여기서 중단합니다. 별도 승인된 공식 설치 절차가 필요합니다.
   이 패키지에는 Python·PostgreSQL·Node·psycopg·tzdata가 포함되어 있지 않습니다.
6. 전체 검사에는 IANA Asia/Seoul 시간대 데이터도 필요합니다. 일반 Windows Python은
   이를 기본 제공하지 않아 공식 tzdata 패키지가 필요할 수 있습니다. preflight가
   KST_TIMEZONE_DATA_MISSING을 표시하면 누락된 상태이며 자동 설치하지 않습니다.

```powershell
Get-FileHash .\oneil-windows-combined-v2-source.zip -Algorithm SHA256
# 신뢰할 수 있는 별도 검증 스크립트/소스와 Python이 있을 때:
python .\tools\verify_windows_offline_bundle.py .\oneil-windows-combined-v2-source.zip
# 소스 폴더에서 네트워크 없는 준비 검사:
python -m oneil_runtime_v2.preflight
# runtime 검사에도 시간대 데이터가 필요합니다:
python -m unittest discover -s tests/runtime_v2 -v
# 이미 신뢰할 수 있는 Python, Node, 시간대 데이터가 준비된 경우 전체 오프라인 검사:
python tools/run_monitor_v2_tests.py
```

preflight의 종료 코드 2는 의도된 "운영 준비 승인 아님"입니다. 자동 재시작에
연결하지 않습니다. 실제 PC에 명령을 실행한 결과가 아니라면 Windows 검증 완료로
표시하지 않습니다. 조합본 aggregate 검사는 core/control/monitor/policy/runtime와 Node
계약 검사를 모두 포함하며 skip을 통과로 처리하지 않습니다. Linux에서 Python 3.12.14,
Node 24.22.1로 검증했으며 Windows 실행 결과는 아닙니다. 실제
PostgreSQL 연결에는 별도로 psycopg가 필요합니다. 기존 Unix-socket PostgreSQL 테스트 도구를 Windows
호환 테스트라고 표시하지 않습니다.

엄격한 정책 워커는 재시작 후 명시적인 정책·원래 제안·현재 증거 등록이 없으면
주문 시도를 차단합니다. 실제 Windows 서비스는 아직 없습니다. 오프라인 SimulationRuntime은 원래 의도만
복원하고 새 현재 증거를 따로 요구합니다. 연결된 simulation 워커의 최종 admission과
모의 전송 직전에 건강 상태를 재검증합니다. 기존 incident journal만으로는 주문을
제어할 수 없고, 실제 legacy 엔진은 아직 fence에 참여하지 않습니다.
자세한 구현 범위는 [ORCHESTRATION.md](../../oneil_runtime_v2/ORCHESTRATION.md)를 확인합니다.

## 3. 재시작은 복구의 시작이며, 주문 허가가 아님

현재 코드에는 순수 재시작 **계획기**와 모의 runtime의 영속 재시작 예산이 있습니다.
실제 프로세스를 실행·종료하는 Windows 감독기는 없습니다. 계획은 5초, 10초, 20초 대기 후 최대 3회, 이후 운영자 확인입니다.
반복 장애가 안정 구간 없이 재시작 예산을 초기화해서는 안 됩니다. 모의 runtime은 재시작 횟수·중지 상태를 SQLite에 영속 저장합니다. 강제 종료 후에는
기존 소유권을 자동 해제하지 않으며, 실제 감독기의 종료 확인·복구 구현과 Windows
전원 장애 시험이 여전히 필요합니다. Task Scheduler 자체의 분 단위 재시작 설정과 이 초 단위 계획을 혼동하지
않습니다. 최종 호스트 설계에서는 하나의 재시작 예산 소유자만 선택합니다.

모든 새 프로세스는 다음 순서를 따라야 합니다.

1. 기존 journal과 core DB를 명시적으로 열고, 없거나 손상되면 중단합니다.
2. 기존/신규 엔진 공통 계정 소유권 fence를 검증합니다. 현재 공유 SQLite 모형은
   참여하는 모의 엔진만 조정합니다. 실제 legacy 적용은 아직 미구현인 게이트입니다.
3. 신규 주문 허가를 내리지 않은 채 기존 UNKNOWN·미체결·부분체결부터 조회합니다.
4. 실제 DB 거래 원장과 완전한 브로커 주문 이력·잔고·현금·체결 인과관계를 대조합니다.
5. 세션·호가·정책·계정·인증 유효성을 새로 검증합니다. 이전 건강 스냅샷은 폐기합니다.
6. 상태가 회복돼도 기존 안전 중단을 자동 해제하지 않습니다. 이미 전송을 시도한
   주문은 응답이 없어도 재전송하지 않습니다. 이력이 없다고 미전송으로 단정하지 않습니다.
7. 명시적인 별도 승인·검토 없이는 실거래나 새 주문을 활성화하지 않습니다.

## 4. 건강 상태와 절전·인터넷 장애

운영 관측값은 최소한 프로세스 생존, 워커 heartbeat 나이, DB 읽기 성공 시각,
완전한 브로커 조회 성공 시각, 디스크 여유, 미확정 주문을 구분해야 합니다.
프로세스 PID가 있다는 이유로 정상으로 표시하지 않습니다. 실패한 API 조회를
"체결 없음"으로 바꾸거나 마지막 성공 시각을 현재 시각으로 덮어쓰지 않습니다.

기본 오프라인 평가값은 루프/heartbeat/의존성 관측 최대 15초, 시계 차이 2초,
디스크 여유 1 GiB입니다. 이는 합성 운영 시험값이며 사용자 투자·손절·배분 규칙이
아닙니다. 실제 관측 빈도와 저장량을 측정한 후 검토해야 합니다.

Windows에서는 GetTickCount64와 QueryUnbiasedInterruptTime을 함께 읽습니다.
전자는 절전 시간을 포함하고 후자는 제외하므로 차이로 복귀 후 절전을 감지합니다.
UTC 시각의 역행·불연속과 루프 지연도 별도로 검사합니다. 이중 시계나 증거가 없으면
정상으로 추정하지 않습니다.
[Windows time](https://learn.microsoft.com/en-us/windows/win32/sysinfo/windows-time),
[QueryUnbiasedInterruptTime](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime).

현재 패키지의 DB/브로커 건강 검사 입력은 테스트용 증거입니다. 실제 인터넷 연결
프로브는 연결하지 않았습니다. 향후 허용된 읽기 전용 어댑터에서 정확한 서비스의
성공·실패·시간초과를 기록해야 합니다. 일반 웹사이트 ping, Wi-Fi 연결, DNS 성공만
가지고 브로커 정상이라고 할 수 없습니다. 프로브에는 주문·취소 요청을 쓰지 않으며,
TLS 오류 우회나 토큰을 URL에 넣는 방식을 쓰지 않습니다.

절전·전원 장애·인터넷 단절 중인 PC는 자기 장애를 실시간 알릴 수 없습니다.
별도 외부 heartbeat 감시가 필요하지만 현재는 구축하지 않았습니다. 외부 감시는
별도 호스트·공유 데이터·비용·알림 대상 검토 후 연결해야 합니다.

## 5. 장애 대응·업데이트·롤백

- **DB 단절/손상/디스크 부족:** 신규 admission은 core에서 차단해야 합니다. 메모리 큐나
  빈 DB로 대체하지 않습니다. journal 쓰기가 실패하면 정상 표시·주문 허가를 하지 않습니다.
- **워커 종료:** 제한된 복구 시작만 허용합니다. 정상 종료·사용자 중지는 재시작하지 않습니다.
- **응답 시간초과·강제 종료:** 전송 여부가 불확실하면 UNKNOWN을 보존합니다. 재전송 금지입니다.
- **절전 복귀:** 지연을 기록하고 조회부터 수행합니다. 놓친 주문을 몰아서 실행하지 않습니다.
- **업데이트:** 새 버전을 별도 폴더에서 해시·테스트 검증 후 중단 상태에서 교체합니다.
  기존 프로세스 종료와 계정 소유권 해제를 확인하기 전에 새 워커를 켜지 않습니다.
- **백업:** core, command journal, 운영 journal의 일관성 있는 복구 지점을 함께 계획합니다.
  WAL 사용 DB의 본 파일만 실행 중 복사하는 단순 백업을 사용하지 않습니다.
- **롤백:** 코드만 되돌리더라도 DB와 주문 원장을 과거로 덮지 않습니다. 양쪽 저널을
  서로 다른 시점으로 복원하면 중복 위험이 생기므로 중단 상태를 외부에서 강제하고
  실제 브로커와 재대조해야 합니다. 운영 기록 삭제는 복구 방법이 아닙니다.
